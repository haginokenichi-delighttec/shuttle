# 送迎ルート最適化 設計方針（v0.4, 2026-10-22）

## 変更履歴
- v0.4: 1日の利用人数は約40名（180名は登録者数）と判明。多回転は「必須」→「オプション」に格下げ。小規模なのでルートプール＋集合分割を本命に格上げ。
- v0.3: 規模を反映。便内の複数回転（多回転）を追加。距離行列は便内ペアのみに削減。
- v0.2: 最大乗車時間を除外。利用プランによる「便（wave）」構造を追加。2段階解法へ。
- v0.1: 初版

## 規模（2026-10-22時点）
- 職員 約10名、車 6台（うち2台は所有者固定）
- 利用者 登録約180名 / 1日約40名、プラン 4（人数に偏りあり）
- 運転者より車が少ない → 車がボトルネック。優先度は「誰が運転するか」の選択に効く

## 規模から見た影響
- 便は最大8つ（4プラン × 迎え/送り）、1便あたり概ね 5〜20名程度
- 6台の総座席数（例: 1台7席で約40席）に対し1便の人数は収まる見込み → 多回転は原則不要
  - ただし歩行器積載枠・介助スキル制約で特定車に集中する場合に備え、多回転はオプションとして残す
- 計算量はごく小さい（1日 40ノード）→ 近似でなく最適に近い解を狙える

## 便（wave）
- 利用プラン p は (到着時刻 A_p, 出発時刻 B_p) を持つ（例 9:00着/12:00発）
- 便 r = (方向, 時刻)。迎え便: 施設到着 ∈ [A_p − ε, A_p]。送り便: 施設出発 ∈ [B_p, B_p + ε']
- 利用者は自プランの迎え便・送り便にそれぞれ1回ずつ乗る
- 既定: 1ルートには同一便の利用者のみ（異なる時刻の混載は要確認・オプション）
- 同じ職員・車は時間が重ならなければ複数便を担当可

## 集合・パラメータ
- U: 当日利用者（座席数, 歩行器有無, 介助レベル need_u∈{1,2,3}, 乗降時間, プラン）
- D: 当日出勤職員（シフト[s_d,e_d], 優先度 p_d, 介助スキル skill_d）
- C: 車両（定員 cap_c, 歩行器積載可否/台数, 所有者 owner_c）
- K: 候補ペア (d,c)。所有車は owner のみ・owner は自車のみ（約 8×4+2 ≈ 34〜42 ペア）
- T_ij: 移動時間行列

## 解法
### Step 1（MVP）: 2段階
- Stage A: 便ごとに OR-Tools Routing（VRPTW）。車両は車種タイプ（定員, 歩行器可否）で表現
- Stage B: CP-SAT で各ルートに (職員, 車) ペアを割当。職員・車ごとに NoOverlap、シフト内、介助スキル ≥ ルート最大need、所有車ルール。目的は優先度ペナルティ＋平準化

### Step 2（本命）: ルートプール＋集合分割（CP-SAT）
- 便ごとに候補ルートを多数生成（Routing を台数・車種・乱数を変えて反復、＋スイープ/挿入ヒューリスティック）。1便10〜20名なら数百〜数千ルートで十分
- CP-SAT で同時最適化:
  - 各利用者を各便でちょうど1回カバー
  - 選んだルートに互換ペアを1つ割当
  - 職員・車ごとに NoOverlap、シフト内
  - 目的: α·移動時間 + β·優先度ペナルティ + 平準化
- 規模が小さいので数秒〜数十秒で最適またはほぼ最適

### オプション: 便内多回転
- 車種タイプごとに回転コピーを用意し「n回転目帰着 + バッファ ≤ n+1回転目出発」

## 目的関数（全体）
min α·総移動時間 + Σ 使用ペア·(F + β·(Pmax − p_d)) + γ·未割当

## 除外した制約
- 最大乗車時間（当面考慮しない）

## 距離行列
- 1日分は 41×41 ≈ 1,700 要素。登録者全員なら 181² ≈ 3.3万要素
- 住所は固定なので、登録者全員分を一度取得してキャッシュ → 日々の計算は API 呼び出し不要（新規利用者の差分のみ）
- Phase1: ハーバサイン×迂回係数(≈1.3)÷平均速度(20〜30km/h)
- Phase2: Google Routes API でサンプル取得し係数校正
- Phase3: API で全件取得・キャッシュ。料金は最新の公式情報で確認。外部送信可否は施設規程を確認
